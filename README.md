## Verification command

From this directory, with Python 3.11 or later, Git, rustup, and a native Rust linker:

```console
python scripts/verify.py --clean
```

This performs a fresh Charon extraction, checks retained artifacts and negative cases, builds the selected Kraken modules and existing arithmetic proof closure, and checks the delivered Lean statements. It records logs and measurements in `evidence/verification.json`. Bootstrap the pinned tools and dependencies as described below first. Tool installation stays in the surrounding workspace's `work/` directory; rustup installs the explicitly pinned Rust nightly in its usual toolchain directory.

For subsequent checks with tools and dependencies already present, use `python scripts/verify.py`. `--local-only` runs policy and source-integrity diagnostics and always reports incomplete verification. A local test pass is not a target proof pass.

Exit codes are 0 for complete automated target checks, 1 for a failed check, and 2 for incomplete checking or a missing prerequisite. Missing tools, skipped artifact tests, missing checks and stale generated artifacts prevent a successful result.

Relative `--lean-bin` paths are resolved against the invocation directory before
subprocesses change working directories. Bootstrap uses the fixed surrounding
workspace `work/` directory shared by extraction, the compatibility builder and
verification; it has no `--work` override. Preserve the documented archive layout.

## Proof and execution boundary

The theorems begin at assembly entry, with the intended limbs and constants
already in the allocated registers. The compact checked representation omits
the MIR operand-value expressions and destination places. Full MIR is retained
for provenance, but the proofs do not establish that the Rust wrapper loads
the intended argument limbs or stores the result into the intended Rust locations.

**Kraken model execution vectors** execute Kraken's AArch64 model through Lean
on the host. They do not execute the original assembly on ARM hardware.
The MIR prefix/suffix evaluator used to prepare those vectors is test
infrastructure and does not prove the omitted wrapper behavior.

## What the bridge does

1. `scripts/bootstrap.py` obtains exact source revisions from `pins.json` and builds the real Charon rustc driver. `scripts/install_lean.py` checks official release archive SHA-256 digests in `lean-release.lock.json` before installing Lean.
2. `scripts/extract.py` invokes Charon on the complete, unmodified target crate for `aarch64-unknown-linux-gnu`, selecting the two functions. It retains the complete LLBC file and copies the assembly subtrees without parsing Rust or maintaining instruction lists. JSON pointers, source Git identities, binary hashes, compiler identity, commands, and the raw artifact hash accompany the extraction.
3. `bridge/kraken_adapter.py` validates the structured operands and templates, substitutes a deterministic legal register allocation, and emits Kraken input. Regeneration compares every generated byte and the complete generated file set. Alternative allocations may share registers only between equal-valued read-only inputs; early outputs cannot overlap any other operand.
4. Lean kernel checks connect `generated/add-check.json` to the exact retained addition assembly and the actual typed program produced by Kraken's parser. They also check operand modes, the `reg` class, early outputs, and all represented options. The character quotation has a separate checked readback equality to the retained file. This compact projection is generated from the retained full operand/template subtree without editing instructions; Python regeneration, JSON pointers and hashes check its relationship to raw LLBC. The five checked representation theorems, their exact statements and axiom census are in [bridge/THEOREMS.md](bridge/THEOREMS.md). They do not establish arithmetic correctness.
5. `proofs/AdditionMachine.lean` checks the addition AST instantiation, decodes that exact program algorithmically, and proves that complete allocated executions agree with canonical executions on all fifteen operand registers and flags. Every written operand must be disjoint from every other operand; read-only inputs may share registers. Whole-program theorems preserve memory and SP for every binding and preserve each physical register outside the written allocation. Incoming flags, scratch contents, memory and SP are arbitrary. Exact statements, hypotheses and axiom counts are in [proofs/THEOREMS.md](proofs/THEOREMS.md).
6. The minimal, unmodified Pasta proof closure in `vendor/pasta/lean` supplies the arithmetic specifications and proofs. The `AdditionNat*` and `AdditionParametric*` modules prove correspondence from actual Kraken execution to the existing `addMod` model. Their candidate data and arithmetic abstractions have kernel checked readback equalities. `proofs/AdditionCorrectness.lean` composes this result with the existing field specification for both Pasta fields, including output bounds, modular addition, complete frames, and an explicit retained-template link in its postcondition. Its hypotheses contain register admissibility and field inputs, with no assumed model correspondence.

7. The multiplication modules decode all 135 actual instructions, project Kraken execution to the existing `mulMont` model, and compose it with the existing field specification for both fields. The public theorem has no model-correspondence premise. It states Montgomery multiplication under the exact upstream `mulContract`, complete frames, and retained-artifact correspondence. Its expanded contract is in [proofs/MUL_CORRECTNESS_THEOREM.md](proofs/MUL_CORRECTNESS_THEOREM.md).

The documented command requires the addition correctness gate to pass before checking multiplication. Both targets have exact public-type audits and kernel-certified carry/binding counterexamples. Current verification status is stated above; archived narrower-policy passes do not certify a changed allocation domain.

Multiplication's representation boundary is specified in
[bridge/MUL_THEOREMS.md](bridge/MUL_THEOREMS.md). Its encoder certificate checks
the complete document against a raw `List UInt8` included from the retained file
using `IO.FS.readBinFile` and `Lean.ToExpr`. File inclusion remains explicit in
the provenance trust boundary. The kernel compares every encoded byte with the
retained bytes while avoiding conversion of a large string literal.

## Supported extraction boundary

The accepted source is exactly the pinned Pasta checkout. The adapter accepts `asm!`, 64-bit general register class operands, `in`, early `out`, and early `inout`, with exactly the represented options `pure`, `nomem`, and `nostack` enabled. It accepts only the straight-line arithmetic instruction forms needed by the selected blocks. It rejects instructions outside its explicit allowlist, memory operands, labels, directives, register modifiers, explicit register declarations, late outputs, `const`, `sym`, label operands, missing operands, undeclared physical registers, reads of uninitialized scratch/carry, and unknown or incompatible represented options.

The generic Rust `reg` class lowers to LLVM `r`, whose 64-bit class contains X0 through X30. The pinned default Linux target reserves X29 through its `non-leaf` frame-pointer policy, leaving thirty potential allocation registers. X19 is admitted: its rejection as an explicit Rust register name does not exclude it from generic allocation. The theorem preserves X19 whenever it lies outside the written allocation. SP and XZR are outside this generic class; XZR is supported as an instruction's literal zero register. The fixed Linux target permits X18 with its default target features. The deterministic artifact allocation keeps its original order, skipping X19 and X29 before appending X19, so the retained programs are unchanged. Other target policies are outside scope; immutable Rust and LLVM source evidence is in `evidence/register-policy.json`.

Immediate logical shifts use `#decimal` amounts from 0 through 63 in 64-bit
registers. Hex/binary shift spellings, register shifts at the bridge boundary,
out-of-range amounts, mixed widths and SP operands are rejected explicitly.

Charon's AST does not retain every source spelling option: for example, the compiler resolves `raw` template processing before this AST is produced. The adapter does not claim to recover discarded Rust syntax. The immutable source gate rejects modified or replacement source rather than accepting arbitrary Rust crates on the strength of the normalized artifact alone. `global_asm!` and `naked_asm!` are not supported.

## GitHub Actions and upload

The included workflows run **Unit and integrity checks** on pushes and pull
requests, and **Full verification** manually or when a release is published.
Both initially use Windows. Actions use immutable commit references; the hosted
image version is recorded per run. Unit CI checks all Python tests, pinned
source/lock integrity, retained extraction links, generated-file freshness and
the source manifest. Full CI bootstraps pinned tools in an isolated runtime,
records fresh extraction provenance against the submitted target baseline, and
executes `python scripts/verify.py --clean`.

Full CI requires a fresh technical `PASS`, actual exit 0, all required proof
stages/audits/negative checks and measurements, and unchanged checked inputs.
Missing tools, omitted proofs, failed or `PARTIAL` verification results fail the
job. Logs, reports, theorem audits, extraction provenance and measurements are
uploaded on success or failure; compiled tools and dependency caches are excluded.
Historical source evidence is left untouched in the original checkout.

To upload, put this project's contents at your GitHub repository root, including
`.github/`, `.gitattributes` and `SOURCE-MANIFEST.json`; commit and push. The job's
checkout recreates the documented `outputs/` layout internally. With workflows
on the default branch, open **Actions → Full verification → Run workflow**.
Publishing a release also triggers that workflow. Full instructions, artifact
paths and automated acceptance criteria are in [.github/README.md](.github/README.md).
No GitHub Actions execution is claimed by the presence of these workflow files.

After intentional source or documentation edits, explicitly update and check the
manifest before committing:

```console
python scripts/source_manifest.py --write
python scripts/source_manifest.py
```

This updates packaging hashes and does not establish proof correctness. CI
checks a submitted manifest without silently refreshing it.

## Pins and rebuilds

`pins.json` fixes Pasta, the extraction Charon revision and Rust compiler commit, the upstream Aeneas library context, Kraken, Lean, and Mathlib. `proofs/lake-manifest.json` fixes transitive Lean packages. `lean-release.lock.json` fixes official Lean archive contents. No floating branch is the source of a verified result.

The target's existing Aeneas pin predates Charon's structured assembly AST. The new LLBC is consumed by this bridge rather than being passed to that older Aeneas executable. Existing arithmetic proofs are reused unchanged. The selected Kraken source originally requested a Lean nightly; the actual selected-module compatibility check uses Lean 4.31.0. The retained upstream Kraken snapshot is unchanged. Three separately hashed patches form the build overlay: the `List.allSome` namespace fix, bounded 64-bit `#decimal` LSL/LSR aliases using existing shifted ORR nodes, and one parser guard allowing XZR destinations in the existing immediate arithmetic branch. Every instruction-semantic body remains unchanged. `scripts/kraken_compat.py` checks exact patch bytes, hashes, source patterns and overlay contents.

`--clean` removes the local Lean build outputs and then recompiles the delivered checks; extraction always uses a fresh Cargo target directory. Fresh extraction compares the complete structured assembly subtrees. Retained raw hashes, JSON-pointer links and every generated byte/file are checked separately; artifacts are not silently replaced. Existing checked release archives and Mathlib caches may be reused in a normal clean check; their role is documented in `RESULTS.md`.

For a fresh Windows workspace, preserve the archive's `outputs/pasta-assembly-verification-bridge/` layout, then run these setup commands from that directory:

```console
python scripts/bootstrap.py
python scripts/install_lean.py
python proofs/bootstrap.py --lean-bin ../../work/toolchains/lean-4.31.0-windows/bin
python scripts/extract.py
python bridge/kraken_adapter.py --artifact artifacts/charon-asm.json --output generated
python scripts/verify.py --clean
```

Extraction regeneration in this procedure is intentional and reviewable: a different local Charon build has different binary identity and may produce different raw LLBC metadata. The retained source/tool pins, templates, operands, and JSON-pointer links must remain consistent. An ordinary verification run never silently accepts an altered binary or updates a stale generated file. `--bootstrap` is also available on the verification command to fetch/build prerequisites, but it does not bypass these provenance checks. Platforms other than the measured Windows host require validation; archive digests for their Lean downloads are pinned without claiming an unperformed platform test.

The separate extraction command is `python scripts/extract.py`; its `--check` mode re-extracts and compares. The adapter command is `python bridge/kraken_adapter.py --artifact artifacts/charon-asm.json --output generated --check`. Intentional source changes require a new pin and artifact review; editing generated instruction files is not an update procedure.

The extraction check also compares the current assembly source bytes and tracked
`Cargo.lock` bytes with their retained provenance hashes. This is stricter than
the portable Git-blob identity: changing line endings requires explicit
regeneration of provenance. Missing or stale hashes fail before extraction.

Every full verification also checks each locked Lean dependency's current Git
revision, repository and source cleanliness. Imported dependency build caches
remain trusted artifacts; the command does not claim to rebuild all Mathlib
dependencies or prove their cached source-to-binary correspondence.

## Trust and proof limits

Lean checks proof terms against the definitions actually imported. A printed or generated Lean file alone is not evidence of verification. Standard Lean logical axioms and the exact axiom census for delivered statements are reported separately from extraction provenance.

The trust boundary includes the Rust compiler and its MIR production, Charon's implementation, the bridge's source selection, JSON normalization/projection and provenance checks, the local tool builds/downloads, file inclusion at elaboration, upstream arithmetic specifications, Kraken's instruction semantics, and Lean's implementation and imported libraries. The MIR prefix/suffix evaluator used to derive executable test inputs is test infrastructure, not a proved Rust wrapper translation. SHA-256 and Git identities detect changed bytes relative to the recorded artifacts; they do not prove faithful extraction or authenticate a compromised host. No compiler, assembler, register allocator, machine code, binary, timing, or hardware verification is claimed.

Kraken's parser uses partial parser combinators, so its complete parser computation is not reduced by the Lean kernel. It produces a candidate typed `Program` during elaboration. Separate total serializers check that candidate: addition against retained assembly text, and multiplication against the retained structured template for every allowed binding. The multiplication JSON encoder checks every retained document byte, including the final LF. The kernel artifact link checks the actual program consumed by the semantics without assuming parser correctness. Interrupted full-envelope and large-string experiments are retained as diagnostics, not accepted proofs. The compact projection preserves the semantic fields used by the checked renderer and metadata predicate. Full raw operands and spans remain retained alongside it.

Both target theorems relate Kraken execution to Pasta's existing arithmetic models for every admissible binding and arbitrary incoming NZCV, scratch contents, memory and SP, then apply the existing field specifications. Read-only operands may share a physical register when their values agree; written operands must be separate from all other operands. The theorems preserve memory, SP and every register outside the written allocation. X29 is reserved; X19 is preserved whenever it is outside the written allocation. Neither public theorem assumes assembly-to-model correspondence.
